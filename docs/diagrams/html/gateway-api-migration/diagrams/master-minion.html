Overview / Master/minion discovery
Step 1 · classify what Kustomize actually applies

Master/minion topology discovery

Every run starts with a full classification of every Ingress in the repo — delegated to scripts/classify_ingress.py (one JSONL line per Ingress) followed by scripts/pair_minions.py (pairing report). The primary case is master/minion topology (common.ingress/ + common.service/); standalone Ingress is the fallback.

1.1 · Built-overlay mode (preferred) — why raw files lie

Repos using base templates contain placeholder hostnames (base-mlflow.example.com) that overlays patch per env. A raw-file classifier sees the placeholder literally, fails to pair it with any master, and HALTs with a spurious "orphan minion" error. So the skill builds each overlay first and classifies the rendered Ingress docs:

# enumerate overlays under common.ingress/ and common.service/
find common.ingress common.service -type f -name kustomization.yaml \
  -path "*/overlays/*" > /tmp/gwm/overlays.txt

# build each overlay, keep only the Ingress documents
kustomize build "$overlay" \
  | yq ea '[select(.kind == "Ingress")] | .[] | split_doc' - > /tmp/gwm/built/<module>-<env>.yaml

Built mode also automatically excludes dead files — YAML on disk that no kustomization.yaml references — because Kustomize never includes them in the build output. Dead files are still surfaced as a diagnostic in state.yaml.discovery.deadFiles[].

1.1 fallback · Raw-file mode

If the repo has no overlays/* structure, or every build yields zero Ingress docs, discovery falls back to a raw grep and records state.yaml.discovery.mode: "raw-fallback". This is a legitimate mode for standalone Ingress repos, not an error.

grep -rIl "^kind: Ingress$" . --include="*.yaml" --include="*.yml" \
  > /tmp/gwm/ingress-files.txt

1.2 · Classify each Ingress

python3 scripts/classify_ingress.py /tmp/gwm/built/*.yaml \
  > /tmp/gwm/classifications.jsonl
# one JSON object per Ingress: classification, reason, hosts,
# hasPaths, hasTls, mergeableIngressType, full annotations map

Classification values: master, minion, standalone, foreign (non-nginx class — skipped, but recorded in state.yaml.discovery.foreign[]), unknown.

1.3 · Pair minions with masters — exit codes are gates

python3 scripts/pair_minions.py --input /tmp/classifications.jsonl > /tmp/pairs.json
# returns topology, pairs[], orphanHosts, orphanMinions, ambiguous, foreign, standalone
ExitVerdictMeaning
0✓ ProceedHappy path — topology is master-minion, standalone, master-only, mixed, or none.
1⛔ HALTOrphan minion(s) or ambiguous pairing — print orphanMinions[].reason and ambiguous[].candidates[] so the user can fix the source.
2⛔ HALTBad input (no classifications).
⚠ Orphan hosts (master declares a host with no matching minion) are a WARN, not a halt — their listeners are skipped by default and surface in report Section 3.2. Pass --include-orphan-hosts to emit listeners anyway.

Feedback loop and interactive mode

  • Minion namespaces are extracted (jq -r '.pairs[].minion.namespace') and fed back to Step 0b for per-namespace preflight status.
  • Invoked without a module path, the skill prints a numbered list of detected migration units and lets the user pick one.
  • The full pair report is stored as-is in state.yaml.topology.
