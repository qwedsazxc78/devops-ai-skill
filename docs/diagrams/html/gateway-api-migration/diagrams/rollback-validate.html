Overview / Atomic rollback + validation
Steps 3–4 · failures are recoverable, by design

Atomic rollback + semantic validation

Conversion is two-phase, each with its own atomicity guarantee. Validation is four sub-steps culminating in scripts/validate_generated.py — 11 semantic checks plus an optional ingress2gateway second-opinion cross-check.

Phase 3A · Temp-dir atomicity

Everything is written to common.gateway.tmp/ first, renamed to common.gateway/ only on success. Any failure before the rename → rm -rf common.gateway.tmp/, common.gateway/ untouched, HALT with a message explaining the target repo is clean. Pre-existing targets HALT without --force (never-clobber).

Phase 3B · Full-content backups, not hashes

Before any in-place edit, every kustomization.yaml that will be modified is backed up in full:

mkdir -p docs/reports/gateway-migration/<slug>/backups/
for env in dev stg prd; do
  cp "common.service/overlays/$env/kustomization.yaml" \
     "docs/reports/gateway-migration/<slug>/backups/${env}-kustomization.yaml.pre-edit"
done
# state.yaml.steps.3B.backups[]: {originalPath, backupPath, sha256}
# SHA256 is for tamper detection ONLY — rollback uses the backup file
# contents, not the hash. This fixes the v1.0 bug where rollback could
# never work.

After each env's HTTPRoutes are written and registered (idempotent yq eval -i ".resources += [...]"), the env is validated with kustomize build. On failure:

  1. Restore kustomization.yaml from the backup file.
  2. Remove every newly created *-httproute.yaml for this env.
  3. HALT with the kustomize error; steps.3B.rollback is stored so --resume retries from the failing env.

4d · The 11 semantic checks

  1. kustomize-build-gateway — gateway overlay builds clean
  2. kustomize-build-service — service overlay builds clean
  3. listener-coverage — every HTTPRoute sectionName resolves to a Gateway listener
  4. httproute-parentref-name — every parentRefs[].name matches a real Gateway
  5. source-hostname-coverage — every source master hostname appears in a listener
  6. source-backend-coverage — every source minion backend Service appears in a generated backendRefs[]
  7. path-coverage — every source path+pathType appears in generated matches[] (ImplementationSpecific / → PathPrefix / normalized)
  8. namespace-consistency — HTTPRoute namespace matches its source minion's
  9. tls-secret-coverage — every source spec.tls[].secretName is in a listener's certificateRefs[]
  10. dead-file-safety — dead files don't leak into built output
  11. ingress2gateway-second-opinion (optional) — our hostnames/backends must be a superset of the upstream tool's (extras like the tls-redirect HTTPRoute are allowed)
python3 scripts/validate_generated.py \
  --target-root      /path/to/target/gitops/repo \
  --module           common.ingress \
  --minion-module    common.service \
  --generated-module common.gateway \
  --env              dev > docs/reports/gateway-migration/<slug>/step4d.json
# overall: fail → HALT · warn → risk register entries · pass → Step 5
# add --no-second-opinion to skip check 11

4c · Second-opinion divergence classes

The normalized diff goes to docs/reports/gateway-migration/<slug>/second-opinion.diff; each divergence is classified and counted in state.yaml.steps.4c.divergenceBreakdown:

  • expected — intentional extras our skill emits (GCPBackendPolicy, Certificate, ManagedCertificate refs, ResponseHeaderModifier, tls-redirect HTTPRoute)
  • formatting — key order, whitespace, field nesting
  • needsReview — anything else; needsReview > 0 → WARN, never HALT
⚠ A 4d listener/path mismatch is treated as a Phase 3A bug — fix the generation, then re-run. If the failure reveals a pre-existing problem in the source Ingress, fix the source instead.
