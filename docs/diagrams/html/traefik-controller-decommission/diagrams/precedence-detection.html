Precedence-aware nginx-class detection

Kubernetes has two ways to bind an Ingress to a controller: the modern spec.ingressClassName field and the legacy kubernetes.io/ingress.class annotation. The verifier mirrors controller precedence: spec wins; the annotation only counts when the spec field is null.

The match rule

An Ingress is counted as an active nginx Ingress when:

spec.ingressClassName == "nginx"
# OR — legacy fallback, only when the spec field is absent
spec.ingressClassName == null  AND  metadata.annotations["kubernetes.io/ingress.class"] == "nginx"

Precedence matrix

spec.ingressClassNamekubernetes.io/ingress.class annotationCounted as nginx?Why
nginx(anything)⛔ YesSpec explicitly binds to nginx
nullnginx⛔ YesLegacy annotation fallback fires
traefiknginx (stale leftover)✓ NoSpec wins — leftover annotation is ignored, exactly as the controllers do
nullabsent / not nginx✓ NoNo binding to nginx by either mechanism

Why this matters for decommissioning

  • A naive grep nginx would false-positive on migrated Ingresses that kept a stale legacy annotation — blocking a decommission that is actually safe.
  • It would also false-negative on annotation-only Ingresses with no spec field — letting an outage slip through.
  • This rule was already GitOps-correct in v1.12.0 and is carried unchanged into this skill.
⛔ Any Ingress matching the rule — in cluster or repo — means the nginx controller is still load-bearing. Step 3 exits 1 (BLOCKED) and commands.sh is never written.
