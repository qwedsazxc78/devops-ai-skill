Inventory & batch plan

Discovery is deterministic script work, not LLM guessing: a bundled Python script walks one env overlay and the operator approves an explicit batch plan before any file is generated or moved.

Step 1 · Per-overlay nginx inventory

inventory_nginx_ingresses.py --overlay-dir common.service/overlays/<env>
# filter: ingressClass == "nginx" only
# result written to state.yaml.inventory[]
# HALT if zero nginx Ingresses found — nothing to migrate

Each inventory entry captures the source file, Ingress name, namespace, and hosts:

inventory:
  - { file: argocd-nginx-ingress.yaml, name: argocd-server,
      namespace: argocd, hosts: [argocd.dev.example.com] }

Step 2 · Batch plan + y/N confirmation

Inventory entries are grouped by host TLD + service criticality into default batches:

BatchContentsRationale
b1Read-mostly servicesLowest blast radius — migrate first
b2Write-heavy servicesMigrate after b1 proves the path
# proposed plan is printed, then the skill waits
batchPlan:
  b1: [argocd-server, grafana]
Proceed with batch b1? [y/N]
⛔ Operator declines → HALT. state.yaml.verdict: HALTED is written with the failing step, and --resume re-runs from Step 2.

Invocation forms decide the scope

FormScopeVerdict path
*nginx-to-traefikInteractive: inventory + propose batches✓ Full Step 1–2 flow
*nginx-to-traefik <env>All services in one env✓ Full Step 1–2 flow
*nginx-to-traefik <env> <batch>Named batch (b1 | b2)✓ Confirm that batch
*nginx-to-traefik <env> <service>Single service✓ Confirm one entry
*nginx-to-traefik --resumeContinue from state.yaml↻ Re-runs failed step
