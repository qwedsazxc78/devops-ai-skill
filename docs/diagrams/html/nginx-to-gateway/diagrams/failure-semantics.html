Failure + halt semantics between phases

Halting at different points in the chain leaves different state behind. The orchestrator records exactly where the chain broke so the right partial resume can be chosen — work already done is never redone.

The three halt patterns

Where it haltsResulting stateResume path
⛔ A halts (C.2) phaseA: failed · phaseB: blocked · verdict: FAIL — B is never invoked Fix A's halt cause, re-run the chain (pass --resume through to A)
⛔ B halts (C.4) phaseB: failed · verdict: FAIL — A's outputs stay intact Resume re-runs C.4 only (--skip-a + --phase-a-state)
⚠ C halts after B, before rendering Both phases completed, combined index.md missing Resume re-runs C.5 only

index.yaml after an A-side failure

phaseA:
  status: failed
phaseB:
  status: blocked      # B was never invoked — nothing to roll back
verdict: FAIL
⛔ A's HALT halts the chain immediately. The orchestrator never invokes phase B against an incomplete class swap.

Clean early exit — --skip-b

Passing --skip-b runs phase A only: C.4 and C.5 are skipped, and the chain halts cleanly (this is not a failure):

phaseB:
  status: skipped
verdict: COMPLETED_A_ONLY

The class swap is live; the resource swap can be chained later with --skip-a --phase-a-state <A's state.yaml>.

Why partial resume is safe

  • No state merging — each phase's state.yaml is self-contained, so re-running one phase cannot corrupt the other's record
  • B's classifier reads A's outputs fresh from --source-state — the orchestrator caches nothing it would have to invalidate
  • The chain run-dir is guarded by C.1: an existing <slug> directory HALTs unless --force is set
